原理
lsassy远程dump lsass的一个工具，其原理是通过安装一个系统服务，并指定服务的imagepath为以下命令来转存 lsass

注：这段命令是一个 Windows 批处理脚本，用于执行一系列操作来转储 lsass.exe 进程的内存，并将结果保存为一个 .ini 文件：

  1. %COMSPEC% /Q /c：这是 Windows 的环境变量 %COMSPEC%，它指向系统的命令提示符（cmd.exe）。通过 /Q 参数，禁止显示启动命令提示符窗口。/c 参数用于指示命令提示符执行指定的命令后关闭。
  2. CMd.Exe /Q /c：这是启动新命令提示符实例，并同样使用 /Q /c 参数来保持窗口不显示。
  3. for /f "tokens=1,2 delims= " %A in ('"tasklist /fi "Imagename eq lsass.exe" | find "lsass""')：这是一个 for 循环，用于获取运行中的 lsass.exe 进程的信息。具体操作如下：
    • tasklist /fi "Imagename eq lsass.exe" | find "lsass"：使用 tasklist 命令列出所有进程，并使用 find 命令过滤出包含 “lsass” 的进程行。
    • tokens=1,2 delims= "：指定分隔符为空格，将进程信息的第一个和第二个字段提取为 %A 和 %B 变量。
  4. do rundll32.exe C:\windows\System32\comsvcs.dll, #+0000^24 %B \Windows\Temp\Xqbxl.ini full：对于每个找到的 lsass.exe 进程，使用 rundll32.exe 执行 comsvcs.dll 中的一个函数来转储内存，然后将结果保存为 .ini 文件。具体操作如下：
    rundll32.exe C:\windows\System32\comsvcs.dll, #+0000^24 %B \Windows\Temp\Xqbxl.ini full：运行 rundll32.exe 执行 comsvcs.dll 中的一个函数，其中 %B 是进程 ID，\Windows\Temp\Xqbxl.ini 是保存结果的 .ini 文件路径，full 是一个参数。

PPLdump

利用的是dll劫持，当一个进程被创建时，它首先会通过“已知 DLL”列表（为了提高效率）去搜索dll，然后在应用程序的目录，系统目录等等……在这个搜索顺序中，“已知 DLL”是最高优先级的。
“已知 DLL” 是 Windows 应用程序最常加载的 DLL，它们被预加载到内存中（即它们被缓存），可以通过查看\KnownDlls对象管理器中目录的内容来查看缓存的dll

关键点来了，在正常的程序启动时，程序加载dll，仅在映射文件时进行验证，即创建节的时候，相比之下PP进程是会进行dll的数字签名验证的过后才能加载，而PPL又和正常程序一样一样，这就是漏洞利用点，因为 DLL 的数字签名仅在映射文件时进行验证，即在创建节时，所以如果能够向\KnownDlls目录中添加任意条目，那么您就可以注入任意 DLL 并在 PPL 中执行未签名的代码。

PTH (hash传递）

如果拿到了某个域用户的ntlm hash，即可使用pass the hash进行攻击，其原理是将该用户的ntlm hash注入当前主机的lsass进程中，然后打开一个新的管理员命令窗口，该管理员命令窗口仍然是本地窗口，但它已经拥有了访问目标用户的权限

PTK

ptk是在域中攻击kerberos认证的一种方式，原理是通过获取用户的aes hmac，通过kerberos认证，可在NTLM认证被禁止的情况下用来实现类似pth的功能。(用的少，如果hash 传递不成功，可以试试)

wmi事件订阅

WMI提供了强大的事件处理系统，几乎可以用于操作系统上发生的任何事件做出相应。

当创建某进程时，通过WMI事件订阅器来执行预先设置的脚本。
其中触发事件的具体条件被称为“事件过滤器”（Event Filter），如用户登录、新进程创建等；对指定事件发生做出相应的称为“事件消费者”（Event Consumer），包括一系列具体的操作，如运行脚本、记录日志、发送邮件等。
在部署事件订阅时，需要分别构建Filter和Consumer两部分，并将两者绑定在一起。

所有的事件过滤器都被存储在一个Root\subscription:__EventFiilter对象的实例，可以通过创建EventFilter对象实例来部署事件过滤器。事件消费者是基于ROOT\subscription:__EventConsumer系统类派生来的类。

DCOM

COM（Component Object Model，组件对象模型）是微软的一套软件组成的二进制接口标准，使得跨编程语言的进程间通信、动态对象创建成为可能。COM指定了一个对象模型和编程要求，使COM对象能够与其他对象交互。这些对象可以在单个进程中，也可以在其它进程中，甚至可以在远程计算机中。在Windows中，每个COM对象都由唯一的128位的二进制标识符标识，即GUID。

DCOM（Distracted Component Model，分布式组件对象模型）是基于COM的一系列概念和程序接口，支持不同机器上的组件间通信。利用DCOM，客户端程序对象可以请求来自网络中另一台计算机上的服务器程序对象。

部分DCOM组件公开的接口中可能包含不安全的方法。执行以下命令，可以列出计算机上所有的DCOM程序组件

目前常利用的DCOM组件有：MMC20.Application、ShellWindows、Excel.Application、ShellBrowserWindow等。

使用DCOM在远程主机上面执行命令，需要具有以下条件：

约束委派

原理

由于非约束委派的不安全性，微软在windows server 2003中引入了约束委派，对Kerberos协议进行了拓展，引入了S4U，其中S4U支持两个子协议：Service for User to Self (S4U2Self)和 Service for User to Proxy (S4U2proxy)，这两个扩展都允许服务代表用户从KDC请求票证。S4U2self可以代表自身请求针对其自身的可转发的Kerberos服务票据(ST1)；S4U2proxy可以以用户的名义请求其它服务的ST2，约束委派就是限制了S4U2proxy扩展的范围。

其中：
S4U2Self（用用户的TGT向KDC请求用户的可转发的ST1，再用这张ST1去发起S4U2proxy请求。） 通过此扩展可以拿到一张标识任意用户身份的ST，它的作用其实是协议转换。有时用户会通过其他协议（例如NTLM或甚至基于表单的身份验证对服务进行身份验证，因此他们不会将TGS发送给服务。在这种情况下，服务可以调用S4U2Self来要求身份验证服务为其自身的任意用户生成TGS，然后可以在调用S4U2Proxy时将其用作依据。**例如服务器service1可以使用它去向KDC请求一张xx用户身份的ST1，服务器service1再用这张ST1去发起S4U2proxy请求。

S4U2proxy（拿用户的可转发的ST1请求用于访问服务器的ST2） 该拓展作用是使得服务器service1使用一张xx用户身份的ST1去向KDC请求一张用于访问服务器service2的ST2（其获取是否能成功的依据是通过判断msds-allowedtodelegateto里的spn值来确定是否可以申请到service2的ST2），这张ST2的身份还是用户的，这样的话网站A就可以利用用户A的权限去访问服务器service2上的文件了。

**漏洞点：若service1对DC的CIFS服务（只是假如，这里攻击效果最大化选用CIFS）存在约束委派，并且service1已经被我们控制，拥有其hash或密码，则可以请求service1自身的TGT（TGT必须通过KDC认证，若能直接获取可省略该步，如能直接mimikatz票据提取到），再以该TGT伪造S4U2proxy请求，以administrator用户权限去访问受委派的CIFS服务，从而获取到ST2，将ST2注入到内存中即可访问对应的服务资源。

1）MS14-068

原理：在kerberos认证过程中通常包含有一个特权属性证书（PAC）,用于验证用户权限，这是一个可选项，可以通过设置include-pac的布尔值来确定AS_RSP阶段返回的TGT是否包含PAC。通常情况下PAC都是会以krbtgt的ntlm hash 作为密钥以某种签名算法（如 eTYPE-AES256-CTS-HMAC-SHA1-96）来进行签名的，这也意味着若没有相关密钥是无法伪造PAC的。
但是！很关键啊，它有三个漏洞点：
如何绕过krbtgt hash签名限制？
KDC实现签名的加密允许所有的签名算法，这就意味着我们可以构造特定的PAC（如使用MD5这种不需要密钥(即krbtgt hash)的签名算法），将其相关信息如sid、用户组等设置为域管对应的信息，那么只要这个PAC能正常生效，那么就可以利用该PAC最后生成的ST，访问域控服务资源；

如何使PAC生效？
KDC能够解析到放在其它位置上的PAC内容。这也意味着即使include-pac的值为false，PAC没有被放在TGT中，放在其它地方PAC内容也能正常解析。

如何将PAC正常嵌入TGT中？
正常情况下PAC是被包含在TGT中的，而后在TGS_REQ阶段将其发送给TGS，TGS只有在TGT正确才会返回ST，在TGS_REQ阶段必须将PAC嵌入TGT中。而
KDC验证缺少PAC的TGT成功后，会再验证不在TGT中 的PAC的合法性。如果2个均验证成功，KDC把PAC中的User SID、Group SID取出来，重新使用进行签名，签名算法和密钥与设置inclue-pac标志位为TRUE时一模一样。并将新产生的PAC加入到解密后的TGT中，再重新加密制作全新的TGT发送给Client，不是TGS。

2）CVE-2020-1472（Zerologon）

（这本应算一个提权漏洞，但我觉得将它归为横向也没问题，毕竟他最终操作的还是域控的机器账户）
 Netlogon 和 DC 交互的过程：

  1. 客户端调用NetrServerReqChallenge方法发送ClientChallenge给服务端
  2. 服务端向客户端返回ServerChallenge
  3. 双方都利用Client的hash、ClientChallenge、ServerChallenge同时计算Session_key
  4. 客户端利用session_key和ClientChallenge函数计算ClientCredential并发送给服务端进行校验。
  5. 服务端也利用Session_key和ClientChallenge函数去计算一个ClientCredential
  6. 服务端对比客户端发送过来的ClientCredential，一致表示通过认证

漏洞点

1）无限次的认证请求、签名校验可以关闭：在认证的整个协议包里面，默认会增加签名校验，这个签名的值是由 session_key 进行加密的，但是我们可以通过在 NegotiateFlags 中，取消设置对应的标志位来关闭这个选项的，将 flag 位设置为 0x212fffff 关闭签名校验。

2）错误使用了 AES-128 加密算法，ComputeNetlogonCredential 函数使用的是名为在 8 位 CFB 模式下使用零初始向量的 AES-128 加密算法，在此情况下，只要设置明文固定为零，就可以在有限的验证请求下获得key为零的情况，从而通过验证。

原理：netlogon认证过程，客户端可以通过设置特定标志位关闭签名校验，而后利用ComputeNetlogonCredential 函数的缺陷配合AES-128及CFB8分组模式，可以在设定特定明文全为0情况下，通过发送大量ClientCredential认证请求，直至服务器那端计算出来的密文 hash 也全是 0，使得认证通过。
认证通过之后，就可以调用 RPC 函数中的 NetrServerPasswordSet2 (Opnum 30) 方法将 DC 的机器账号的密码重置为 0。（NetrServerPasswordSet2 方法允许客户端为域控制器使用的帐户设置一个新的明文密码）

导致脱域主要是因为 AD 里面存储的机器密码跟本机的 Lsass 里面存储的密码不一样，正常情况下，Domain 中有一个 DC 和一个服务器，因为他们有一个共享的 Secret（机器帐户密码），可以使用 Secret 进行彼此通讯建立加密通道，借助 Zerologon 攻击，攻击者主要更改 DC 的计算机帐户的密码，即是单方面更改 Secret，那么就没有办法进行彼此通讯建立加密通道。
